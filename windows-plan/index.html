    Windows Server 2025 — pre-work plan¶

    Planning only. No Windows captures or enforcement code ship in this repo yet. This page maps what already works, what's missing, and a phased path to bring winget-installed Windows Server apps into the same evidence-based access model the Linux side uses.

    1. Where capture stands today¶

    treadmark already produces a 1.0-windows footprint — a file and registry diff against a clean baseline. Its CI smoke test exercises this on a Windows runner (IIS via the Windows Feature channel, Datadog via winget/MSI), but those footprints are 1–7 day workflow artifacts, deliberately not release assets — no Windows footprint is committed anywhere in the corpus. It captures:

    • Windows services reconstructed from HKLM\System\CurrentControlSet\Services (image path, start type, run_as identity, dependencies), with OS-background-churn services filtered out.
    • Scheduled tasks (principal, run level, triggers, command).
    • Files with owner and DACL ACE strings (files only — directory DACLs are recorded as null), classified (iis, service_binary, program_files, programdata, system32, driver, scheduled_task, startup, …).
    • access_hints[] per principal (the paths a service/task plausibly needs, with provenance) and risks[] (kernel_driver_installed, service_image_nonstandard_path, service_custom_account, autostart_service_as_system, scheduled_task_elevated, world_writable_file).

    Two structural limits are baked in and must be stated in any Windows doc:

    • SAM opacity. Windows accounts live in the SAM, not a readable file, so treadmark references identities (a service's run_as, a file's owner) but never enumerates the local accounts/groups an installer created. "The install created account X" is always [needs-runtime-confirmation] on Windows.
    • Feature-channel invisibility. Install-WindowsFeature payload is pre-staged in the component store, so a Feature install can produce almost no diff (IIS's services are already present on the image). winget/MSI is the channel with real footprint visibility — pick winget-native candidates.

    2. The enforcement gap map (Linux primitive → Windows analog)¶

    Linux primitive Windows analog Maturity
    scoped sudoers systemctl grants sc.exe sdset — per-service SDDL granting start/stop/query to a group SID (single-tenant scope); JEA proxy functions for per-command / per-site scoping — both in-box primitive exists; no generator
    POSIX ACL + default ACL icacls grants with (OI)(CI) inheritance (cleaner than POSIX default ACLs) fine; DACLs replace, so review needs before/after icacls
    pam_group at login GPO Restricted Groups / Add-LocalGroupMember — token built at logon, so "flip requires logoff" holds, but membership is standing, not session-scoped no session-scoped equivalent
    journalctl -u per unit Event Log Readers builtin group, or per-channel ACL (wevtutil sl /ca:) per-channel scoping is coarse
    loginctl linger — (services are machine-scoped) N/A
    ownership entries icacls /setowner + explicit DACL fine
    service-account hygiene SeServiceLogonRight + deny-interactive via a secedit INF; prefer virtual accounts (NT SERVICE\<svc>) or gMSA over custom accounts INF stub pattern designed
    MAC (SELinux/AppArmor) AppLocker / WDAC, AuditOnly first; regenerate rule hashes on-host (AppLocker uses Authenticode PE hashes, not flat-file sha256) skeleton designed

    The de-facto stub set already sketched in treadmark's runbook corpus: icacls-<app>.ps1, service-account-<app>.ps1, logon-rights-<app>.inf, restricted-sid-<app>.ps1, local-groups-<app>.ps1, firewall-<app>.ps1, applocker-<app>.xml. None are generated by code today — they are hand-authored artifacts.

    2a. IIS worked design — the vendor-native stack, single-tenant (2026-08-23)¶

    Scope: one team per host (our current support boundary), Server 2022/2025 (the delegation surface is unchanged between them). The rule is the same as the Linux role-evals: use what the vendor ships, document what it covers, and let our profile layer fill only the recorded gaps.

    What Microsoft ships for exactly this¶

    Mechanism (all in-box) What it delegates Where it's configured
    WMSVC (Web-Mgmt-Service feature) + IIS Manager Permissions Remote IIS Manager for non-admins: connect to their site over HTTPS :8172 with AD credentials; they see only delegated features administration.config (grants via the ManagementAuthorization API), WMSVC registry enable + service
    Feature Delegation Which system.webServer sections the site connection may Read / Read-Write (auth, default docs, compression, SSL settings flags, …) section locks in applicationHost.config
    Site start/stop via the delegated site connection The team's own site object comes with the site connection
    NTFS + per-pool virtual accounts (IIS AppPool\<pool>, the default identity since IIS 7.5) Content ACLs per class: team Modify on content, pool identity Read (+ Write only on App_Data-class paths) icacls (OI)(CI)
    Certificate private-key ACLs ("Manage Private Keys") Read on their cert's key in LocalMachine\My, imported non-exportable CNG key DACL
    Centralized Certificate Store (Web-CertProvider) File-based cert management: certs are <hostname>.pfx in a directory IIS loads by SNI convention — cert rotation becomes a file operation on a path we can ACL Enable-WebCentralCertProvider
    AD CS autoenrollment Platform-owned issuance/renewal (the acme_please analog) GPO
    Event Log Readers / per-channel wevtutil /ca: The journalctl analog, incl. CAPI2 for TLS diagnostics builtin group
    JEA (in-box PowerShell) Exact-command proxy functions under a virtual account for whatever the rows above cannot express role-capability + session registration

    The honest gap list (what the vendor path does NOT delegate)¶

    The R6 finding repeats on Windows: the product delegates feature configuration, not operational control. A delegated site connection cannot:

    • recycle its application pool (Application Pools is server-scope — and pool recycle is the single most common day-2 op);
    • edit bindings or bind a certificate (bindings + http.sys SSL binds are server-scope);
    • restart W3SVC/WAS, or iisreset.

    Single-tenant fills, in order of preference: sc.exe sdset on W3SVC+WAS granting start/stop/query to <hostname>-app_restricted (whole-service control is correct when the host is one team's — this is the sudoers-verbs row); a small JEA endpoint for the two operations SDDL cannot express (Restart-AppPool, Bind-SiteCert with the team's site/pool/thumbprint as ValidateSet). Multi-tenant later = drop the SDDL row, widen the JEA file. Never granted, any tenancy: applicationHost.config and inetsrv\config (write there is root-equivalent for every site on the host), key export, store-wide cert rights.

    SSL, filesystem — the two stated team needs¶

    • SSL: non-exportable cert in LocalMachine\My; team group gets private-key Read + the JEA Bind-SiteCert; renewal is autoenrollment/ACME dropping the renewed cert, team rebinds; CAPI2 read for diagnostics. Where the team fully owns cert files, CCS converts rotation into a file drop on an ACL'd path instead.
    • Files: content root team-Modify, pool identity Read + App_Data-Write, deny pool-identity Write on web.config (the config→ACL doctrine: the service cannot rewrite its own config — doubling as web-shell persistence defense), per-site log dir Read.

    Stub set to implement (extends the §2 list)¶

    wmsvc-<app>.ps1 (feature install, registry enable, service, ManagementAuthorization::Grant for the AD group), delegation-<app>.ps1 (section locks), sdset-<app>.ps1 (with sc.exe sdshow snapshot first — the rollback), jea-<app>.psrc/.pssc (the two proxy functions), certkey-<app>.ps1 (key ACL + non-exportable import), plus the existing icacls-<app>.ps1 / local-groups-<app>.ps1 / firewall-<app>.ps1. Verify probes (the _verify-remote.sh analog over PS-Remoting): team can start/stop site + recycle pool + rebind cert + write content; team cannot write applicationHost.config/web.config-as-pool, cannot export the key, cannot touch a foreign service. The verification vehicle question in §6 is answered since the KVM tier landed: tofu/modules/windows-vm + the smoke-test-windows pattern.

    The flip stays: remove from app_full + force logoff + klist purge (tokens are logon-time).

    3. What a Windows --access-vars would emit¶

    A parallel declarative_access_windows_* sketch (a separate module — the Linux exporter is POSIX-path-bound and refuses Windows footprints today):

    • services → sc.exe sdset SDDL grant list per role group;
    • folders → icacls grants (with the replace-semantics warning);
    • AD group → local-group placements (GPO Restricted Groups);
    • service accounts → SeServiceLogonRight INF + deny-interactive;
    • AppLocker skeleton (AuditOnly) flag.
    • Not applicable: linger, quadlets.

    Apply vehicle is an open question: ansible.windows (win_acl, win_group, win_service) vs DSC vs raw PowerShell stubs. Recommend a declarative_access_windows role in the collection as the target, with the PowerShell stubs as the bridge.

    4. The winget corpus loop — TESTED AND RULED OUT (2026-08-23)¶

    The loop below was the plan. It does not work on our substrate, and the reason is structural rather than fixable by configuration. winget cannot be used to build the corpus over SSH. Evidence: evidence/windows-2025/winget-recon.json and evidence/windows-2022-desktop/winget-recon.json, produced by scripts/winget-recon.sh.

    What was tried¶

    The probe (scripts/winget-recon.ps1) walks four escalating paths to reach winget: PATH lookup → per-user Appx registration → register the staged or provisioned package → bootstrap via Microsoft.WinGet.Client + Repair-WinGetPackageManager. It ran on Server 2025 Core and, after that failed, on Server 2022 Desktop Experience.

    The finding¶

    MSIX deployment requires an interactive session. The last bootstrap path fails with:

    0x80073D19  An error occurred because a user was logged off.

    That is the AppX Deployment Service refusing to deploy in a network logon, which is what SSH (and WinRM, and therefore Ansible over either) gives you. winget ships as an MSIX package (Microsoft.DesktopAppInstaller) that must be registered into a user profile before it can launch at all — so the failure is not "install denied", it is "winget.exe does not exist for this session".

    Three corollaries, each verified rather than assumed:

    • It is not a privilege problem. Keys land in administrators_authorized_keys, so sshd mints a full unfiltered admin token. On the same transport we ran Install-WindowsFeature, sc.exe sdset, Set-Acl on applicationHost.config, and Register-PSSessionConfiguration — all elevated operations, all successful.
    • It is not an edition problem. Desktop Experience has a healthy Appx stack where Core does not (appx_module and dism_module both present, C:\Program Files\WindowsApps enumerable — on Core that directory is ACL'd to TrustedInstaller and the DISM-backed Get-AppxProvisionedPackage throws a COMException). Desktop still fails, because the blocker is the session type. There is therefore no reason to leave Server Core, which is what the fleet runs.
    • Ansible does not change this. Ansible connects over the same SSH network logon and shells out to the same PowerShell; there is no winget module in ansible.windows, so driving it would mean win_shell calling an executable that is not present. Ansible would fail identically.

    Also observed: the 2022 images carry no provisioned App Installer at all (provisioned, registered_current_user and registered_all_users were all empty), consistent with packer/common/windows/install-winget.ps1 skipping silently when build/cache/winget/ is unpopulated.

    Scope of this finding — what was NOT tested¶

    The result above is specific and should not be over-read. Tested and failed: deploying/registering MSIX from an SSH session, and reaching winget as Administrator over SSH on both editions. Not tested: invoking an already provisioned winget.exe by absolute path from a SYSTEM scheduled task.

    That distinction matters, because the SYSTEM route is the mainstream way winget is automated (Intune Win32 apps, ConfigMgr, PDQ all do it) and two of the specific blockers we hit do not apply to it:

    • SYSTEM can read C:\Program Files\WindowsApps, where our elevated Administrator session got access-denied;
    • a scheduled task runs outside the SSH session's job object, which is independently necessary for long installs (holy-qcow already uses this pattern in seal.ps1 and the firstboot agent);
    • provisioning itself is automatable non-interactively — Add-AppxProvisionedPackage -Online is the DISM offline API, and is how the packer build installs App Installer today.

    Known limits of the SYSTEM route even when it works: no user-scope packages, the msstore source is unavailable, --accept-source-agreements is required, and Microsoft does not formally support it.

    The SYSTEM route was then tested — and found the real problem¶

    scripts/winget-escalate.ps1 ran both remaining routes on a 2025-core clone. Evidence: evidence/windows-2025/winget-escalation.json.

    The mechanism works. The package is missing. The SYSTEM scheduled task ran exactly as intended and reported:

    identity: nt authority\system
windowsapps: enumerable but NO DesktopAppInstaller dir

    Two things follow. First, the approach is sound: SYSTEM can enumerate C:\Program Files\WindowsApps, which the elevated SSH session could not — so the ACL blocker named above is real and the scheduled task genuinely clears it. Second, and decisively, there is no App Installer payload on the deployed clone at all — not unregistered, absent. The same holds on 2022 Desktop, where Get-AppxProvisionedPackage, Get-AppxPackage and Get-AppxPackage -AllUsers all came back empty.

    So the honest verdict is narrower and more useful than "MSIX can't work over SSH": no holy-qcow Windows image currently delivers a usable winget to a deployed clone. That contradicts install-winget.ps1's "2025 ships it" assumption and the smoke test's provisioned-package assertion, and is filed as a holy-qcow issue. Until an image actually carries the package, winget cannot be evaluated further on this substrate — and once one does, the SYSTEM scheduled task is the route to use, because its only failure here was the missing payload.

    (The runas equivalent, Start-Process -Credential, was tested in the same run and produced no output — inconclusive, and moot while the package is absent. It remains theoretically interesting because CreateProcessWithLogonW performs an interactive-type logon rather than SSH's network logon; note /noprofile would defeat it, since MSIX registration writes into the user profile.)

    What to use instead¶

    The corpus goal is unchanged: capture real installs whose footprints show services, files, ACLs and registry keys — the thing the Feature channel cannot give us (§1). Any ordinary installer satisfies that; only MSIX is blocked. Both alternatives are Ansible-native and Appx-free:

    Channel Module Notes
    Direct MSI/EXE ansible.windows.win_package No package manager at all; closest to how these apps are actually deployed. Each app needs a pinned URL and silent-install flags.
    Chocolatey chocolatey.chocolatey.win_chocolatey Plain PowerShell/.NET install, no Appx, works over SSH. Large server catalog (nginx, postgresql, mongodb, redis, rabbitmq, grafana, telegraf, jenkins).

    The candidate list built for this round (scripts/winget-candidates.yml, 39 packages across 8 categories with a service: hypothesis per entry) is channel-agnostic and carries over unchanged — only the resolver changes. scripts/winget-recon.sh and the windows-lib.sh harness it uses are likewise reusable; re-point the probe at choco search or at URL reachability and the same evidence shape falls out.

    The original loop, for whichever channel replaces winget¶

    1. treadmark all init — all, not files: without the registry baseline the model still builds and still exits 1, but with services: [] and the reason buried in registry.note.
    2. install the package silently;
    3. settle ~20s — services keep registering after the installer returns;
    4. treadmark footprint --app <pkg> --report footprint-<pkg>.json;
    5. re-baseline --force before the next app.

    Success is exit code 1 AND the report file exists — a crashed run also exits 1. Note exit 0 means "no file delta", which a registry-only change can produce; inspect the report rather than trusting the code. Add cells to matrix-windows.yml (not matrix.yml — Windows has its own matrix and vars contract, see §2a). Run treadmark from the MSI-installed treadmark.exe: there is no Python on these images, and the frozen binary cannot be uninstalled mid-loop by a package under test (a failure treadmark hit live with Python.Python).

    5. Verification story¶

    There is no Windows analog of the Linux systemd init container or the EC2 SSH-apply loop yet. Options: a Vagrant/Hyper-V VM, or an EC2 Windows AMI with WinRM. Whatever the vehicle, the apply→probe→revoke shape carries over: apply the stubs, confirm a restricted group can sc.exe start/stop its services and read its dirs but not others, then revoke. SDDL has no --tags cleanup analog — capture sc.exe sdshow before sdset for rollback, and secedit /export before an INF apply (user-rights assignment has replacement semantics).

    6. Open questions¶

    • SDDL grant idempotency and reversibility (sdshow snapshots as the undo).
    • Verification vehicle (Vagrant vs EC2 Windows + WinRM) and cost.
    • Remoting choice (WinRM vs SSH) and its interaction with logon-token group refresh at the flip.
    • The flip on Windows = remove from the AD/local group + force logoff; RDP session termination story.
    • Whether registry "config" surfaces belong in profiles at all, or stay sc.exe config-only.

    7. Phased plan¶

    • P1 — a Windows exporter that emits review documents only (no enforcement) from existing footprints; publishable into this repo's docs/apps/<app>/ structure.
    • P2 — generate icacls + local-group stubs per footprint.
    • P3 — sc.exe sdset service grants + a revocation path.
    • P4 — a verification vehicle and CI.

    Each phase ends with something publishable, matching the Linux side's evidence-first discipline.
